## 2. 本机 Docker 环境是怎么配起来的（后续轮次若需重装/排障，照此办理）

### 2.1 版本坑（花了两轮才定位）

第一次装的是国内镜像站的 **Docker Desktop 4.1.1**（2021 年版本）。症状极具误导性：

- 客户端能用、WSL 发行版能起、`docker version` 有输出（客户端 20.10.8）
- 但**守护进程永远起不来**，`docker info` 连不上

根因：**4.1.1 的 WSL2 集成与本机 WSL 2.7.14 存在代差**。
解法：从官网下载 **4.90.0**（`https://desktop.docker.com/win/main/amd64/Docker%20Desktop%20Installer.exe`）。

> **网络注意**：`desktop.docker.com` 直连会被重置，必须走代理：
> `curl -x http://127.0.0.1:7890 -L -o ...`
> 阿里云镜像站只有 4.1.1，国内其他镜像站只有「Windows 容器引擎」（不适用 Linux 镜像）——别浪费时间。

### 2.2 数据落 E 盘的做法（联结 + 经受住重装）

Docker Desktop 的数据目录固定读 `%LOCALAPPDATA%\Docker\wsl`。**用目录联结把它指向 E 盘**：

```
C:\Users\23224\AppData\Local\Docker\wsl   →(Junction)→   E:\DockerData\wsl
```

**关键点：这个联结在「卸载 4.1.1 → 装 4.90.0」之后原封不动**，所以数据一直留在 E 盘。

> 踩坑：`mklink` 在 bash 里写会被引号/转义吞掉，**写成 `.ps1` 脚本文件再执行才可靠**（脚本要**纯 ASCII**——PowerShell 5.1 按 GBK 解析含中文的 `.ps1` 会破坏字符串终止符）。

### 2.3 Docker Hub 拉不动 → 给引擎配代理

国内直连 Docker Hub 会超时：

```
failed to authorize: DeadlineExceeded: failed to fetch oauth token:
Post "https://auth.docker.io/token": dial tcp <IP>:443: i/o timeout
```

**解法**：在 Docker Desktop 的引擎配置里加代理（配置在设置文件里，与镜像源方案相比更干净）：

```json
"DockerEngine": {
  "proxies": {
    "http-proxy": "http://127.0.0.1:7890",
    "https-proxy": "http://127.0.0.1:7890",
    "no-proxy": "localhost,127.0.0.1"
  }
}
```

配好重启后 `docker info` 会显示 `HTTP Proxy: http.docker.internal:3128`（Docker Desktop 的内部转发口），即生效。
配完 `eclipse-temurin:21-jre` 等基础镜像一次拉通。

> 若某次拉取仍偶发超时：**先把基础镜像单独 `docker pull` 拉全**（带重试循环），再 `compose build`，
> 构建就能全部命中缓存，不再触发 registry 鉴权。

基础镜像清单（构建要用，建议保持已拉取状态）：

```
maven:3.9-eclipse-temurin-21      802MB
eclipse-temurin:21-jre            482MB
mysql:8.0                         1.1GB
nginx:1.25-alpine                 75.4MB
redis:7-alpine                    57.8MB
```

### 2.4 内存护栏（**必须保留，否则会把宿主机卡死**）

**症状**：容器构建期间宿主机 31.2 GB 内存只剩 **0.8 GB** 可用，用户在桌面上操作直接卡屏。

**根因**：Docker Desktop 走 WSL2 后端时，**内存上限不在 Docker 自己的设置里，而在 `%USERPROFILE%\.wslconfig`**。
（改 Docker 设置里的 `MemoryMiB` 对 WSL2 后端**无效**——实测 `docker info` 仍显示 15.22GiB。）

**已落地的配置**：

```ini
[wsl2]
memory=8GB
processors=6
swap=2GB
autoMemoryReclaim=gradual
```

生效后 `docker info` 显示 `Total Memory: 7.756GiB、CPUs: 6`，构建全程宿主机稳定 **18.4~18.9 GB 可用**，不再卡。

> **改动后必须 `wsl --shutdown` 再重启 Docker Desktop** 才生效。
> **紧急止血**：`wsl --shutdown` 能立刻把被 WSL 虚拟机占住的内存还给宿主机。

## 3. 实测发现的问题清单

### 3.1 【已修·必现 bug】redis 健康检查永远失败，导致后端起不来

**这是本报告最重要的一条 —— 它会让任何机器上的部署都失败。**

**现象**：

```
Container deploy-redis-1  Up 2 minutes (unhealthy)
dependency failed to start: container deploy-redis-1 is unhealthy
```

blog-server 因 `depends_on: redis: condition: service_healthy` 被门禁挡住，永远起不来。

**根因**：`deploy/docker-compose.yml` 的 redis 服务里，健康检查用了 `$${REDIS_PASS}`（compose 转义 → 容器内展开 `${REDIS_PASS}`），
**但该服务没有 `environment:` 块，变量根本没传进容器**：

```
$ docker compose exec redis env | grep REDIS
REDIS_VERSION=7.4.11          ← 只有这个，没有 REDIS_PASS
$ redis-cli -a "$REDIS_PASS" --no-auth-warning ping
AUTH failed: WRONGPASS invalid username-password pair or user is disabled.
```

即空密码认证失败。**Redis 服务本身是好的**（`--requirepass ${REDIS_PASS}` 由 compose 在宿主机侧展开，密码设对了），**纯粹是健康检查误报**。

**修复**（已应用，位于 redis 服务定义中）：

```yaml
    environment:
      REDIS_PASS: ${REDIS_PASS}
```

修复后 redis 立即转为 healthy，blog-server 正常启动。

> **同类隐患自查项**：其他服务的 healthcheck 若引用容器侧变量，同样必须确认该变量已通过 `environment:` 注入。
> `DeployAssetsM12Test` 是纯文件断言测试 —— 它解析了 compose 的拓扑与关键参数，但**「healthcheck 引用的变量是否已注入」这一条没覆盖**，
> 所以这个 bug 一路走到了真机部署才暴露。**建议本轮补一条契约测试钉死它**（见 §4 M13）。

### 3.2 【已确认·非缺陷】容器内首次 AI 调用偶发 4002

**现象**：容器刚重建后头两次 `/api/ai/summary` 返回 `4002「AI 服务暂不可用」`，之后全部正常。

**排查过程（供参考，避免重走）**：

1. 容器内 `getent hosts api.deepseek.com` → 解析正常
2. 容器内直连 `https://api.deepseek.com/chat/completions` 带真 Key → **HTTP 200，返回 "OK"**
3. 用 app 数据库里存的模型名 `deepseek-v4-flash` 实测 → **HTTP 200**
4. 管理员「连通测试」接口 → **两模型都 ok=true**
5. 特意做了冷启动复现：`docker compose restart blog-server` → 等 healthy → **立即**连打 3 次摘要 → **三次全成功（0.5~0.6s）**

**结论：不是代码缺陷，是瞬时 DNS 抖动。** 同一晚容器构建阶段也出现过 `repo.maven.apache.org: Temporary failure in name resolution`，
稍后重试即通 —— 同一个根因：**WSL2 内部 DNS（`192.168.65.7`）偶发抽风**。

> 对 Qwen Bot 的要求：**不要为了\"修\"这个去改 AI 模块的代码**。这是环境抖动，
> 代码侧已按设计把这类失败归入 4002（不暴露厂商细节）——行为是正确的。
> 若将来要加固，正确方向是**在 `OpenAiCompatClient` 层对「连接/DNS 类瞬时异常」做一次快速重试**，而不是改错误码映射。

### 3.3 【待办·真实不一致】`SPRING_PROFILES_ACTIVE: docker` 指向了一个不存在的 profile 文件

compose 里 blog-server 注入 `SPRING_PROFILES_ACTIVE: docker`，但仓库里只有：

```
backend/src/main/resources/application.yml
backend/src/main/resources/application-prod.yml
```

**没有 `application-docker.yml`**。目前能跑通是因为配置项全部由环境变量注入、`application.yml` 直接读 `${BLOG_DB_URL:...}` 这类占位符。
但这意味着 **`application-prod.yml` 里的所有覆盖项在容器部署时都没生效** —— 是潜在的口径不一致，需本轮处理。

4. **构建提速（改前/改后对比，真机同一 daemon，Engine 29.7.2）**：

   | 场景 | 改前（裸 Central + go-offline 层缓存） | 改后（阿里云镜像源 + cache mount，删 go-offline） |
   |---|---|---|
   | 全新构建（prune 后冷缓存，代理 7890 未开） | **11m02s**（635 个依赖全走 Central 龟速下载） | **1m02s**（mvn 全程 51.9s，635 个依赖 100% 命中 aliyun，Central 零请求） |
   | 只改代码的增量构建（层缓存失效） | go-offline 暖缓存**仍要 397.8s**（依赖树解析每次重走） | **51.8s**（package 单次解析，下载零网络） |
   | 无任何改动的重复构建 | 秒级（pom 层命中） | **~10s 全 CACHED** |

   提速主因排序：①国内直连 Central → 阿里云镜像（10~20 倍）；②删
   `dependency:go-offline`（它每次都完整重走依赖树解析，是纯冗余步骤）；
   ③cache mount 保跨构建/跨镜像层重建的仓库持久化。
   **cache mount 遮蔽陷阱（本轮实测抓出的静默失效）**：挂载 `/root/.m2`
   整目录会把镜像层 COPY 进去的 settings.xml 一起藏掉——提速措施①
   在②生效前完全静默失效且构建"照样成功"；必须只挂 `/root/.m2/repository`
   子目录（回归锁 `dockerfileUsesCacheMount` 三条断言全部机器钉死）。
   **syntax 钉版陷阱**：`# syntax=docker/dockerfile:1` 会让每次 build 前
   先拉 docker.io 前端镜像——无代理的国内环境直接超时炸构建（M13 首跑
   真实踩中）；Engine 29.x 内建前端原生支持 cache mount，故意不钉，
   回归锁反向拦截"照教程补回"。
